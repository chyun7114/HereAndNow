# TestContainer 재사용 구조 검증 계획

## 1. 검증 목적

`static + singleton` 기반 TestContainer 재사용 구조가  
기존 컨테이너 매번 생성 방식 대비 **테스트 수행 시간을 유의미하게 단축하는지 검증**한다.

또한 단순 성능 개선뿐 아니라 아래 항목을 함께 확인한다.

- 재사용 구조가 실제로 동작하는지
- 반복 실행 시에도 일관된 성능 개선이 나타나는지
- 테스트 신뢰성과 데이터 독립성이 유지되는지

---

## 2. 검증 대상

### 비교군 A. 기본 방식

- 테스트 실행 시마다 TestContainer를 새로 생성
- 컨테이너 startup 비용이 매 테스트에 포함됨

### 비교군 B. 개선 방식

- `static + singleton` 기반 TestContainer 재사용
- 동일 JVM 내에서 컨테이너 재생성 방지
- startup 비용 제거

---

## 3. 검증 시나리오

## Case 1. 전체 테스트 스위트 실행 시간 비교

### 목적

재사용 구조 적용 전후의 **전체 테스트 수행 시간 차이**를 비교한다.

### 방법

- 동일 테스트 스위트를 기준으로 비교
- `./gradlew clean test` 기준 실행
- 워밍업 1회 이후 본 측정 5회 수행
- 각 실행 시간 기록 후 평균 산출

### 측정 항목

- 총 테스트 수행 시간
- 평균 수행 시간
- 최소 / 최대 수행 시간

### 기대 결과

- 재사용 구조 적용 시 수행 시간이 명확하게 감소
- 예: `59s → 32s`

---

## Case 2. 반복 실행 안정성 비교

### 목적

일회성 결과가 아닌 **반복 실행에서도 일관된 성능 개선 여부**를 확인한다.

### 방법

- 동일 테스트 스위트를 5~10회 반복 실행
- 각 실행 시간을 기록하여 비교

### 측정 항목

- 각 실행 시간
- 평균
- 표준편차

### 기대 결과

- 재사용 구조가 모든 실행에서 더 빠른 결과를 보임
- 실행 시간 편차가 과도하게 크지 않음

---

## Case 3. 컨테이너 생성 횟수 검증

### 목적

TestContainer가 실제로 재사용되고 있는지 확인한다.

### 방법

- 컨테이너 startup 시 로그 출력
- 여러 테스트 클래스 실행 시 로그 발생 횟수 확인

### 측정 항목

- 컨테이너 startup 로그 출력 횟수
- 컨테이너 생성 시점 로그

### 기대 결과

- 기본 방식: 테스트 실행마다 컨테이너 생성
- 재사용 방식: 동일 JVM 내에서 1회만 생성

---

## Case 4. 데이터 오염 여부 검증

### 목적

컨테이너 재사용으로 인해 **테스트 간 데이터가 공유되지 않는지** 확인한다.

### 방법

- 테스트 1: 데이터 생성
- 테스트 2: 초기 상태를 가정한 조회
- 테스트 순서를 변경하여 반복 실행

### 측정 항목

- 테스트 결과 일관성
- 데이터 잔존 여부

### 기대 결과

- 테스트 순서와 관계없이 동일 결과 유지
- 데이터 오염 없이 테스트 독립성 유지

---

## 4. 통제 조건

공정한 비교를 위해 아래 조건을 동일하게 유지한다.

- 동일 코드 베이스 (브랜치)
- 동일 테스트 대상 및 개수
- 동일 실행 환경 (PC, CPU 상태)
- 동일 JDK 및 Gradle 버전
- 동일 DB 이미지 및 TestContainer 설정
- 백그라운드 작업 최소화

---

## 5. 실행 방법

### 전체 테스트 실행

```bash
./gradlew clean test
```

### 반복 실행 (예시)

```bash
for i in {1..6}
do
  echo "run $i"
  ./gradlew clean test
done
```

## 7. 기대 효과

- 컨테이너 startup 비용 제거를 통한 테스트 시간 단축
- 개발 피드백 루프 개선
- CI 실행 시간 감소

## 8. 추가 고려 사항

- 컨테이너 재사용 시 데이터 정리 전략 필수

- 병렬 테스트 환경에서는 추가 검토 필요
